# 🌿 FloraGuide AI

Веб-приложение для ухода за комнатными растениями.

- **Поиск растений** по названию и описанию проблемы.
- **Свои растения в профиле**: указываете дату посадки, а система рассчитывает, в какие дни поливать.
- **Чат для каждого растения**: вопросы об уходе и диагностика проблем отвечает собственная экспертная система, а не обёртка над внешней нейросетью.

## 🛠 Технологический стек

### Backend
| Технология | Назначение |
|---|---|

## 🚀 Установка и запуск

### Что нужно установить заранее

- [Git](https://git-scm.com/)
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) (должен быть запущен)
- [Python](https://www.python.org/downloads/) 3.11 или новее
- [Node.js](https://nodejs.org/) 20 или новее

Локально устанавливать PostgreSQL **не нужно**: база работает в Docker.

### 1. Клонирование репозитория

```bash
git clone <URL-репозитория>
cd floraguide-ai
```

### 2. База данных (Docker)

Из корня проекта:

```bash
docker-compose up -d
```

Будет запущен PostgreSQL 18 с расширением pgvector. База доступна на порту **5433** (не 5432, чтобы не конфликтовать с локальным PostgreSQL, если он установлен). Данные хранятся в томе Docker и сохраняются между перезапусками.

Проверить, что контейнер работает:

```bash
docker ps
```

### 3. Backend

Все команды выполняются из папки `backend`.

```bash
cd backend
```

**Создать и активировать виртуальное окружение:**

```powershell
# Windows (PowerShell)
python -m venv venv
.\venv\Scripts\activate
```

```bash
# macOS / Linux
python3 -m venv venv
source venv/bin/activate
```

В начале строки терминала должно появиться `(venv)`.

> Если вы используете Anaconda и в приглашении стоит `(base)`, выполните `conda deactivate` перед активацией venv, чтобы использовался именно он.

**Установить зависимости:**

```bash
pip install -r requirements.txt
```

**Создать файл настроек `.env`:**

```powershell
# Windows
copy .env.example .env
```

```bash
# macOS / Linux
cp .env.example .env
```

Откройте `.env` и задайте секретный ключ для JWT-токенов. Сгенерировать его можно так:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Пример содержимого `.env`:

```env
DB_USER=postgres
DB_PASSWORD=postgres
DB_HOST=127.0.0.1
DB_PORT=5433
DB_NAME=floraguide_db

SECRET_KEY=сюда-вставьте-сгенерированный-ключ
```

> ⚠️ Файл `.env` не должен попадать в Git. Каждый разработчик создаёт свой.

**Создать таблицы в базе данных:**

```bash
alembic upgrade head
```

**Заполнить базу начальными данными:**

```bash
python -m app.seed
```

> Скрипт запускается как модуль (`-m`) именно из папки `backend`, иначе Python не найдёт пакет `app`. Повторный запуск безопасен: если данные уже есть, скрипт ничего не изменит.

**Запустить сервер:**

```bash
uvicorn app.main:app --reload
```

Документация API (Swagger) откроется по адресу: <http://127.0.0.1:8000/docs>

### 4. Frontend

Откройте **новый терминал** (бэкенд должен продолжать работать).

```bash
cd frontend
npm install
```

Создайте файл `frontend/.env.local`:

```env
NEXT_PUBLIC_API_URL=http://127.0.0.1:8000
```

Запустите сервер разработки:

```bash
npm run dev
```

Приложение откроется по адресу: <http://localhost:3000>

### Краткая шпаргалка

```bash
# один раз
docker-compose up -d
cd backend && python -m venv venv && .\venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env          # и задать SECRET_KEY
alembic upgrade head
python -m app.seed

# каждый раз при работе
docker-compose up -d            # если контейнер остановлен
uvicorn app.main:app --reload   # терминал 1, из backend с (venv)
npm run dev                     # терминал 2, из frontend
```

## 🗄 Работа с базой данных (Alembic)

Проект использует Alembic для миграций: схема БД меняется без потери существующих данных. Команда `alembic upgrade head` меняет **структуру** таблиц, а не их содержимое, и применяет только ещё не выполненные миграции.

**Если вы изменили модели в `app/models/`:**

1. Сгенерируйте миграцию:
   ```bash
   alembic revision --autogenerate -m "описание изменений"
   ```
2. **Откройте созданный файл в `backend/alembic/versions/` и проверьте его.** Autogenerate иногда ошибается, например переименование поля может превратиться в «удалить колонку и создать новую», что приведёт к потере данных.
3. Примените миграцию:
   ```bash
   alembic upgrade head
   ```

**Полезные команды:**

| Команда | Что делает |
|---|---|
| `alembic current` | текущая версия БД |
| `alembic history --verbose` | история миграций |
| `alembic downgrade -1` | откатить последнюю миграцию |
| `alembic heads` | показать «головы» (должна быть одна) |

> ⚠️ `alembic downgrade` удаляет данные из откатываемых таблиц. `downgrade base` сносит всё.

**Полный сброс базы (удаляет все данные):**

```bash
docker-compose down -v
docker-compose up -d
cd backend
alembic upgrade head
python -m app.seed
```

### Схема базы данных

| Таблица | Назначение |
|---|---|
| `plant_categories` | категории растений |
| `plant_species` | виды растений: условия содержания, описание, вектор для поиска |
| `plant_parts` | части растения (лист, стебель, корни…) |
| `visual_issues` | симптомы, их причины и решения, вектор для поиска |
| `users` | пользователи |
| `user_plants` | растения пользователя: дата посадки, последний полив, интервал полива |

## 🧠 Экспертная система

> **Статус:** Описанное ниже является архитектурой и планом реализации.

Главная идея проекта: диагностика проблем и рекомендации по уходу строятся на **собственной базе знаний и собственной машине логического вывода**, а не делегируются внешней языковой модели. Нейросетевые компоненты, если они используются, только преобразуют текст пользователя в структурированные данные и ничего не решают сами.

### Принцип работы

```
Сообщение пользователя
        ↓
[1] Понимание текста: фраза → симптомы (структура)
        ↓
[2] Контекст растения: вид, дата посадки, последний полив, сезон
        ↓
[3] Машина вывода: правила → гипотезы с уверенностью
        ↓
[4] Данных мало? → уточняющий вопрос → обратно к [1]
        ↓
[5] Ответ: диагноз + что делать + «почему я так решила»
```

### Компоненты

| Компонент | Описание |
|---|---|
| **База знаний** | Симптомы (с синонимами), причины, правила «симптомы + условия → причина» и данные об уходе по видам. Хранится в YAML/JSON-файлах и таблицах БД. |
| **Машина вывода** | Применяет правила к ситуации конкретного растения. Уверенность в гипотезах считается с помощью **коэффициентов уверенности** (certainty factors, как в системе MYCIN): подтверждающие правила объединяются по формуле `CF = CF₁ + CF₂ · (1 − CF₁)`. |
| **Контекст** | Данные из `user_plants` и `plant_species`: когда последний раз поливали, оптимальная освещённость и влажность, сезон. Благодаря этому ответы персональные. |
| **Понимание текста (NLU)** | Сопоставление фразы пользователя с известными симптомами через словарь синонимов и **векторный поиск** (FastEmbed + pgvector). |
| **Диалоговый модуль** | Если две лучшие гипотезы близки по уверенности, система задаёт уточняющий вопрос, который лучше всего их различает. Диагноз выдаётся, когда уверенность превышает порог. |
| **Модуль объяснения** | Показывает, какие правила сработали и почему система пришла к выводу. |
| **Расписание полива** | Интервал рассчитывается из вида растения, сезона, освещения и условий содержания, а также корректируется по отметкам пользователя. |

### Пример правила

```yaml
- id: overwatering_1
  cause: overwatering
  if:
    - symptom: yellow_lower_leaves
    - context: days_since_watering < 0.5 * watering_interval
  cf: 0.7
  explain: "Нижние листья жёлтые, а полив был недавно: корни могут переувлажняться."
```

### Планируемая структура модуля

```
backend/app/services/expert/
├── knowledge/      # симптомы, причины, правила (YAML/JSON)
├── nlu.py          # текст → симптомы
├── context.py      # сбор контекста растения
├── engine.py       # машина вывода, коэффициенты уверенности
├── dialog.py       # выбор уточняющего вопроса, пороги
├── explain.py      # объяснение вывода
├── schedule.py     # расчёт расписания полива
└── responder.py    # формирование ответа по шаблонам
```

### Роль языковых моделей

Ответ системы формируется детерминированно из шаблонов на основе вывода движка, поэтому он воспроизводим и объясним. Языковая модель (при необходимости) может использоваться только как необязательный «переписчик», который делает готовый ответ более читаемым, не добавляя новых фактов. Без неё система продолжает работать полностью.

## ❓ Частые проблемы

| Проблема | Решение |
|---|---|
| `container name "/floraguide_postgres" is already in use` | `docker rm -f floraguide_postgres`, затем снова `docker-compose up -d` |
| `port is already allocated` | порт 5433 занят: измените порт в `docker-compose.yml` и `DB_PORT` в `.env` |
| `password authentication failed` | пароль в `.env` не совпадает с `POSTGRES_PASSWORD` в `docker-compose.yml` |
| `ModuleNotFoundError: No module named 'fastapi'` | не активировано виртуальное окружение: `.\venv\Scripts\activate` из папки `backend` |
| `ModuleNotFoundError: No module named 'app'` при запуске сида | запускайте из `backend` командой `python -m app.seed` |
| `RuntimeError: SECRET_KEY is not set in .env` | добавьте `SECRET_KEY` в `backend/.env` |
| `Multiple head revisions` в Alembic | в `alembic/versions/` лежит лишняя миграция, проверьте `alembic heads` |
| `extension "vector" is not available` | используйте PostgreSQL из `docker-compose.yml`, а не локальный |
| Ошибка bcrypt при регистрации (`__about__`, `72 bytes`) | `pip install "bcrypt==4.0.1"` |
| Фронтенд не может обратиться к API (CORS) | проверьте, что бэкенд запущен и открываете `localhost:3000`, а не другой адрес |
